# 第五阶段计划审阅与执行修订

2026-10-12。原计划可作为范围依据，但以下修订优先；修订后进入执行。

1. 现状必须重新核对。现有调度器已经没有 isInitialized；绑定订阅 stop 清理及首次加N次提醒已由Codex修复。中文验收报告中的6项通过保留，不重复把已修项描述成缺失。计数是状态集合中的客户数，不是已确认的 SQL COUNT DISTINCT。代码位置由执行者补齐。
2. 每日提醒仅针对北京时间今天零点之前的、当前仍待处理的入站消息；今天8:29或8:30的新消息均不能单凭处于待处理状态进入昨日提醒。消息发生时间和首次查到时间分开，模拟事件显式给定。无可信发生时间时明确记录限制。
3. 使用现有 ACTIVE/CLOSED 状态语义；不得直接用不存在的 PENDING/REPLIED/IGNORE状态字符串判断。确认关闭的消息不参与，昨天达到提示上限但仍ACTIVE的参与。
4. 当地日期、08:30时间点及最近每日提醒日期分别表示。当前时间未到08:30不能补做；错过多天仅补当日一次，不能补发多日轰炸。一次每日输出不改变常规次数或调度时间。同一次评估中常规与每日同时到期，合并一次输出，各自状态正确推进。
5. 去重记录须按工作账号和客户持久化。当前绑定客户被排除时不要记作已经提示；当天08:30后解绑仍可补一次。输出失败不得静默记为成功。数据库写入与外部通知不能天然保证崩溃窗口内恰好一次，明确恢复策略和剩余限制，不虚假承诺。
6. 继续沿用可注入 TimeProvider；无需强制全部改java.time.Clock。若抽取纯函数便于本地测试则适量抽取，不强迫当前Android依赖代码在JVM运行。
7. 解绑旧绑定和保留新绑定是两组独立测试，不能先用B2覆盖B1再声称同时验过B1。18:30和22:00、跨日、首次恢复都验证。stop/start仅是调度生命周期，不等于进程重建；额外清除内存并从持久化恢复验证，实际设备进程重建单独标注。
8. 最小非破坏性迁移，真实版本号替代X/Y；保存旧素材、指导、提醒字段，增加迁移保留数据测试。
9. 工作账号隔离作为数据层验证，不扩展登录、多设备同步或账号切换UI；按复合身份检验，不把未确认的登录功能写进范围。
