# SASALELE 业务闭环与新提醒规则开发验证计划

## 1. 当前实现事实与缺口分析
*   **1.1 跨工作账号隔离**
    *   *事实*: 现有代码已引入 `ClientKey(workAccountId, clientId)` 概念。
    *   *缺口*: 需要全面盘点 `ReminderScheduler`, `ClientRepository`, `GuidanceMessageDao` 是否所有查询和缓存均严格使用了复合键，是否存在依然只依赖 `clientId` 的漏洞。
*   **1.2 定时解绑与补做 (18:30 / 22:00)**
    *   *事实*: `UnbindScheduler` 具备 `lastUnbindTime` 和时区判定逻辑。
    *   *缺口*: 需通过测试证明：若设备离线，跨越了解绑点后重启，在错过的时间点**之前**绑定的客户会被清除，而在错过的时间点**之后**（设备离线期间）新绑定的客户必须保留。
*   **1.3 助手启停与进程重建**
    *   *事实*: 调度器可能存在 `isInitialized` 单例锁或重复启动协程的风险。
    *   *缺口*: 服务 `stop()` 时需要明确取消协程作用域（`Job.cancel()`），`start()` 时需重新读取 DB 恢复状态。
*   **1.4 提醒去重、计数与状态跃迁**
    *   *事实*: `ReminderEntity` 具有状态字段，红点使用 `count(distinct clientId)`。
    *   *缺口*: 需进一步验证达到“追加 0 次”（即首次提醒后不再重复）的逻辑边界；需确认“旧消息重放”被精准拦截，且解绑当前客户后，该客户暂存的待处理状态能立即被重新评估输出。
*   **1.5 [新增] 8:30 每日工作开始提醒**
    *   *事实*: 尚未实现。
    *   *缺口*: 需新增独立于常规“重试间隔”的每日一次扫表机制。

## 2. 核心状态与时间规则定义
*   **身份标识**: 绝对不可使用单纯的 `clientId`。全部状态映射必须基于 `(workAccountId, clientId)` 联合主键。
*   **消息身份**: `(workAccountId, clientId, messageId)`。同一消息重复到达，更新时间戳无效，不增加重试次数，不重置等待时间。
*   **时间基准**: 统一注入 `java.time.Clock`，所有时间判定强依赖 `Asia/Shanghai` 时区，严禁使用设备默认时区偏移进行计算。
*   **8:30 每日提醒规则**:
    *   触发条件: `status == PENDING` 且 `lastDailyReminderDate < 今天 8:30`。
    *   排他条件: 已经被标记为 `REPLIED` 或 `IGNORE` 的不参与；当前绑定的客户不参与。
    *   副作用: 不重置该客户原本的 `retryCount` 和 `nextScheduleTime`。作为附加提醒合并输出。每天只执行一次，哪怕多次重启。错过 8:30 后的当天首次启动立即补做。

## 3. 最小修改范围与持久化方案
*   **数据库修改 (非破坏性迁移)**:
    *   修改 `ReminderEntity`: 新增字段 `lastDailyReminderTime: Long = 0L`。
    *   在 `AppDatabase` 中添加 `MIGRATION_X_Y`，使用 `ALTER TABLE` 语句增加字段，避免清空已有历史。
*   **代码修改层**:
    *   `DailyReminderScheduler`: 新增独立组件或整合入 `ReminderScheduler`，依托持久化时间戳过滤。
    *   `ReminderScheduler`: 规范化 `start(scope)` 和 `stop()` 方法。
*   **验证层**:
    *   提供 `TestClock` 实现，便于时间快进与定格。

## 4. 可注入时钟自动化测试矩阵
**分类 A：纯业务规则单元测试 (src/test/，无需设备)**
1.  **消息去重与上限测试**: 发送消息 M1 -> 触发首提 -> 发送 M1 -> 验证重试次数不重置、不追加；配置上限为 0 次时，不触发第二次调度。
2.  **状态跃迁测试**: 标记 M1 为 `REPLIED`，再次发送 M1，验证无反应；发送 M2，验证重新触发提醒。
3.  **8:30 提醒测试 - 常规**: 客户昨天达到提醒上限 -> 时钟调至今天 8:31 -> 触发每日提醒 -> `lastDailyReminderTime` 更新。
4.  **8:30 提醒测试 - 重启与补做**: 时钟在 8:20 关机 -> 调至 10:00 开机 -> 补做 8:30 提醒；再次重启 -> 不重复提醒。
5.  **8:30 提醒测试 - 连日未处理**: 停留 3 天未处理 -> 每天 8:30 均能稳定触发一次。

**分类 B：设备环境与集成测试 (src/androidTest/，需连入专用模拟器)**
1.  **跨工作账号隔离测试**: Account A 绑定 Client X，Account B 收到 Client X 的消息 -> 验证提醒**未**被 Account A 的绑定行为排除。
2.  **解绑恢复补做测试**: 时钟调至 18:00 建立绑定 B1 -> 离线 -> 18:35 建立绑定 B2 -> 重新调度 -> 断言 B1 被自动解绑，B2 被保留。
3.  **进程重建测试**: 写入待处理提醒至 Room -> 手动调用 `scheduler.stop()` -> 模拟进程重建调用 `start()` -> 断言重新读取并恢复红点状态。

## 5. 界面与人工验证清单
仅使用本地“模拟聊天页”，不操作微信：
1.  **红点与通知验证**: 产生到期事件后，检查是否触发 `ReminderNotifier` 的闪动、红点；在系统设置调整声音/震动，检查应用输出是否符合预期。
2.  **解绑排除恢复**: 绑定客户 A -> 发送客户 A 的模拟新消息 -> 断言无红点、无声音 -> 解绑客户 A -> 断言红点立刻出现。
3.  **排行榜独立性**: 绑定客户 A -> 点击排行榜客户 B -> 验证面板内容切换到 B，但顶部头像和底层接待状态依然是 A。

## 7. 潜在歧义记录
1.  **8:30 并发问题**: 如果某消息恰好在今天 8:30 分到达，它是否既触发“首提”又被算作“每日提醒”？*计划设定：每日提醒仅针对之前就处于 PENDING 且尚未经历过今日日间提醒的实体，8:30 之后的新消息正常走追加逻辑，不重复算作日间遗留。*
2.  **多设备/多账号在线**: 纯本地存储时，工作账号切换是否会看到别的账号的红点？*计划设定：UI 查询应严格绑定当前登录的 `workAccountId`。*
