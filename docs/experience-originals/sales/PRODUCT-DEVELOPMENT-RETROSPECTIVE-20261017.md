## 1. 复盘结论与证据口径

这次开发完成了从微信场景探索、浮窗原型、云端业务接入到工作机实际使用的推进。用户在本对话决定将 v26 作为第一个正式版。核心架构逐渐稳定为：销售主动截屏识别客户，按工作号和客户标识匹配方舟记录，服务端生成并共享画像，手机提供销售指导、话术辅助、跟进列表与素材，最终操作由销售完成。

最值得保留的是：在设备和平台条件不齐时，用可替换接口及合成数据继续开发；复用既有方舟与画像能力；把凭据和模型调用集中在服务端；用持久画像、任务和缓存支持多工作机；实际使用反馈持续推动产品收敛。

最需要纠正的是：已有需求与已有资源没有一直贯彻到真实调用链；故障定位有时过早围绕应用代码展开；模型约束一度偏离销售工作的判断方式；功能增加快于界面层级和发布基线的维护。多次需要用户发现入口缺失、状态丢失和业务表达问题，才补上本可前置的检查。

这里不把所有返工都视为浪费。设备兼容、平台分页语义、模型的真实输出形态，需要试验才能发现；应减少的是缺少观测条件的重复试验，以及已经有证据却没有及时采用的判断。

## 4. 关键决策复盘

### 4.1 从持续读取转为主动截图与人工绑定

**当时知道什么**：节点、可访问窗口、模拟器登录和输入法存在复杂条件；历史安全警告有记录，但不能归因到某一个动作。核心目标是在私聊现场辅助销售，不是建立全自动微信控制系统。

**为什么这样选**：主动截图把会话获取变成销售明确发起的动作；静态图片可以用本地样本开发，人工绑定降低名称识别与同名匹配对自动流程的依赖。它削弱了对持续节点读取的依赖，但并没有消除系统捕获、厂商保护和 OCR 的约束。

**结果与代价**：主体开发不再被微信模拟器登录完全卡住；代价是逐次授权、手动切换客户、截图不完整和标题误识别。不能说这是“零风险方案”或自动判定当前客户。

**下次方法**：先分别验证捕获可用性、身份可读性和业务数据可用性，不将三个未知捆成一次长链路。给每条链路保留可替换的输入和失败入口。[S1–S3]

### 4.2 手机轻客户端，云端保存配置、画像和任务

**当时知道什么**：销售应拿手机直接用；用户不希望销售配置 IP、连接开发电脑或办理人员登录；已有稳定服务器资源可落实。

**决定**：HTTPS 服务承接方舟凭据、模型密钥、画像和工作机授权；客户端固定签名，管理员发机一次配置，后续覆盖升级；SQLite 持久卷优先于新增复杂基础设施。

**结果与代价**：多工作机可以复用同一客户画像，凭据不必进 APK；代价是部署、证书、设备撤销、备份和容量都成为产品的一部分。40GB 只是总盘容量，不能单独证明长期存储一定够用；本次未获得持续增长数据。

**复盘判断**：这是贴合规模的方案。需要改进的是让资源填写、部署包、镜像、APK 和工作机版本始终有一份对应表，而不是靠多轮对话串起来。[S6][S11][S25]

### 4.3 从飞书读历史摘要转为方舟聊天按需生成

**当时知道什么**：飞书能用于一部分身份与历史资料，但当次审计只有 20.6% 的记录有非空摘要；这些记录也不能代表全部业务客户。方舟基础资料本身不是销售画像。

**决定**：从旧画像作业抽出可复用能力；不直接调用带全账号快照与飞书写入副作用的批处理；以工作号+客户标识为键，读取有限聊天，生成持久画像，失败保留旧结果，相同输入复用。

**结果与代价**：主链路摆脱飞书覆盖不足；增加了模型契约、生成任务、覆盖范围、旧版本更新和缓存一致性责任。

**应区分的判断**：10 月 13 日先做只读接入是明确的阶段目标，不应事后指责其“为什么没生成”。但 10 月 12 日已知道摘要稀少，此后主页面仍应清楚区分基础资料和生成画像，不能让“匹配成功”看起来等于“画像完整”。[S4][S5][S6][S11]

### 4.4 不先解决全部历史缺口，用活跃样本打通链路

**证据**：用户手机有较早聊天，方舟网页没有对应文本；页面的系统分配事件与接口取得的一条非文本记录相符。另一个活跃客户在网页与接口都能取得文本。

**决定**：先以有文本的活跃样本验证匹配、生成、缓存和草稿；平台是否只保留三个月、历史能否批量恢复暂列待确认。

**复盘判断**：这个收敛是正确的，因为历史保留问题不妨碍验证当前活跃客户链路。但不能因主链路跑通就忘记覆盖缺口；画像质量需在输入不足时有合理预期。

**下次方法**：准备至少四类样本：近期活跃且有文本、长期未联系、仅系统事件、同名跨工作号。它们回答不同问题，不用一个客户承担所有验收。[S12]

### 4.5 复用既有 DeepSeek，而不是让旧配置决定产品路线

**已确认的失误**：我沿用了旧画像工程的 Kimi 配置，遇到 429 后先围绕该账户额度定位。错误分类本身有证据，错在把旧模块当前配置当成了本产品应使用的通路，忽略用户已提供的话术 DeepSeek key。

**纠正**：单独建立销售模型配置，画像、帮我回、润色共用用户已授权的 DeepSeek；配置缺失不静默回退 Kimi。随后合成与限定真实样本生成、缓存复用得到验证。

**下次方法**：复用模块前写清“复用哪些代码、使用哪个产品配置、凭据来源在哪里、生产怎样挂载”。只核对存在性与配置身份，不把 key 再次索要或打印。模型比较、谷价批量与低参数模型替换保留到链路稳定之后。[S13]

### 4.6 业务判断不能退化成核实问卷

**问题**：早期提示词把身份、事实和承诺约束写得太广，造成正常家长语境也被质疑、院校/培训地点线索难以进入业务判断、缺失项清单压过行动建议。

**责任**：这不是用户没有讲清楚行业，而是我在设计时把降低错误当成主要目标，没有给“依据有限信息推进销售工作”足够权重。用户纠正后，我还曾解释格式问题与提示词问题的区别，没有及时回应其对设计倾向的批评。

**纠正原则**：客户陈述默认是可用工作依据；正常语境允许合理角色和阶段判断；实质矛盾才核对；一次只补问影响下一步的关键缺口。个案往来可承接，不伪造当前课程政策、付款到账或已执行安排。判断有依据，不意味着必须拒绝所有推断。

**实现结果**：business-v3 共同调整画像、回复、润色和指导；扩展需求、目标线索、安排与业务推断字段，输出预算同步增加。真实模型合成案例验证了部分表达改善；真实总体质量仍需样本评审，不能用程序回归数量替代。[S22]

## 5. 返工案例与根因分类

| 案例 | 已确认根因或事实 | 当时容易误判什么 | 下次应改变什么 |
|---|---|---|---|
| release 启动闪退 | 隔离同配置 release 复现 IllegalAccessError，关闭局部优化后启动成功；用户后续能进入 | debug 或编译成功代表正式包能运行 | 每次发布先用签名 release 在干净测试环境启动，再进业务验收；不是只跑 debug |
| 微信空白截图 | 代码中有首帧处理、丢帧和诊断缺陷；用户关闭共享保护后能截微信 | 一条空白帧等于持续全黑，或没有标准 SECURE 就一定无限制 | 第一轮即做桌面/其他 App/微信/系统截屏/系统保护设置对照；采阶段与帧数再定位 |
| 复现后没有记录 | 状态清理会删除消息，进程内状态不持久；预设 logcat 未抓到异常 | 用户没复现，或者没有错误 | 先验证诊断可以跨清理/重启保留，再安排用户操作；工具失败由开发者承担 |
| 标题变成返回箭头和未读数 | 旧选择依赖 OCR 返回顺序；改为几何区域与候选规则 | OCR 识字能力差是唯一问题 | 先区分“选错文字框”与“框内识错字”；修复前者不宣称后者也解决 |
| 客户有微信聊天但方舟无文本 | 两个系统覆盖不同；平台只保留三个月尚无证据 | 匹配错、接口坏、平台统一过期，三者任选其一 | 用同账号、同客户、同日期的网页/API/手机对照，再换活跃样本验证链路 |
| 画像“格式错误” | 可解析 JSON 中无值对象与验证器的 null 约定不兼容，拒绝整份画像 | 模型不会输出 JSON，或任何兼容都必须放松内容校验 | 将语法、结构归一化、语义验证分层；合法未知兼容，有值仍核对证据 |
| Android 草稿返回异常 | 旧手写 HTTP 桩不稳定，换实际 FastAPI 路由后合成链路通过；旧异常根因未完全查清 | 自动把测试工具失败算作产品失败 | 测 HTTP 行为用实际路由，假上游替代方舟和模型；保留失败，不虚构修复因果 |
| 编辑补充问题后指导消失 | 结果 state 的 remember 键包含输入，提交时还先清空 draft | 用户以为编辑就是要丢弃旧结果 | 草稿、输入、输入快照分开；成功后替换，失败保留；只在真正换客户/任务类型时隔离 |
| 工作号选择闪退 | Service overlay 使用普通 Dialog，token=null；Activity 测试不能覆盖 | 组件测试通过代表浮窗交互通过 | 关键交互在实际窗口宿主测试；本项目优先面板内确认，而非新增窗口 |
| 选完仍显示选择入口、每次获取 | 真机原现象完整根因未确认；实现了选择持久化、列表缓存和失败保留，用户随后确认正常 | 把推测的生命周期原因写成唯一根因 | 可说采取了哪些改动、问题后续未再出现，不把伴随改动全部当作已证实因果 |
| 提醒列表首次同步失败 | 日期上界引入额外一天；过滤后空页被误当重复页；另有 total 不可靠 | 联系人确实为空，或直接提高超时就能解决 | 翻页进展以原始有效 ID 判定，筛选与分页分离；固定边界样本验证平台语义 |
| 物料图片发成链接 | 内容指向图片不等于已实现图片文件分享 | 换个按钮文案就算图片分享 | 验收实际 payload/MIME/URI 和接收端效果；失败不悄悄降级为链接 |
| 漏斗有类型、没有新增文本入口 | 最初开发说明已有添加文字要求，但真实页面只补了图片 | 把补齐原要求当作用户不断加需求 | 用原需求逐项走实际主入口，检查新增、读取、使用、删除和再次打开 |
| 提醒复测初始候选不存在 | 合成服务器沿用前轮 done 状态；重置后通过 | 产品丢数据或同步失败 | 测试夹具每轮初始化，重要失败先排查工具、账号与状态 |

这些案例分属环境、代码、数据、协议、配置、产品和测试工具。下一次应先分类再修复，不用一套“再改点代码、再让用户试”的节奏处理所有问题。

## 6. 产品过程：哪些反馈是新增，哪些本应做到

### 6.1 既定原则，不能算后来才想到

10 月 10 日计划和 Android 初始说明已要求：一次聚焦一个任务、不要把功能和诊断堆同屏、素材支持添加文字与图片、生成结果可编辑、有无画像都能润色、销售不配置技术环境。后来仍出现演示聊天列表、长技术标识、缺少文本新增、结果不能编辑等问题。

**复盘判断**：主要是需求落实与验收清单没有贯穿真实调用链。原型阶段允许合成数据，不代表正式入口可以长期保留模拟行为；模块里有一个组件，也不代表实际工具条路由用了它。用户不应反复承担找遗漏的工作。[S3][S15][S24]

### 6.2 使用中形成的新决定

以下更接近正常产品演化：画像由飞书必要依赖改为方舟独立生成共享；工作号选择放设置并在提醒页直达；同事号需要持久忽略且可恢复；点击跟进卡复制备注；对素材增加类型筛选。它们基于真实使用暴露的需求或明确调整，不宜全部归为最初遗漏。

但新增入口后仍要看全流程。例如有筛选却没有创建相应类型的入口，反映的是一次局部交付没有检查原有完整性，不能因为“本次只改筛选”就不报告。

### 6.3 值得保留的范围收敛

- 不等待全部历史恢复，先跑活跃客户。
- 知识库未接入前不急着对“帮我回”作业务质量验收。
- 先用既有模型打通，不先做模型比较、小模型部署或夜间调度。
- 不把所有联系人都预先生成画像；按需与缓存先解决当下需求。
- 跟进先用最近方向和人工处理状态，不凭缺少证据的意向评分做排行榜。

这些不是为了少做，而是避免同时引入多个无法归因的未知。需要保留待办，否则阶段性收敛会被误记为永久放弃。

## 7. 验证、协作与交付方式复盘

### 7.1 有效的做法

1. **生产数据与合成验证分离**。UI、任务、失败状态可以先用可控响应验证；少量限定真实样本核对方舟语义与模型表现，减少对真实客户的重复试验。
2. **实际接口配假上游**。它比手写近似 HTTP 桩更能回答 Android 能否接住业务返回的问题。
3. **失败保留旧结果**。画像、指导、联系人缓存和工作号列表逐步采用这一原则，体现日常使用的连续性。
4. **固定签名与覆盖升级**。多轮更新保留配置和数据，避免每次发版重新发机。
5. **版本化部署与健康核对**。哈希、镜像标识、SQLite 备份、只更新 API、检查旧代理，为回溯提供条件。存在脚本不等于完整恢复演练已做，二者仍要分开。
6. **用户及时给出业务判断**。用户把需求从“证明身份”拉回“有限信息下采取行动”，也纠正了模型选择、验收优先级与不直观图标。这些反馈不仅是审美偏好，而是产品定义的一部分。

### 7.2 需要我承担的改进

- 不只复述用户最近一句话，要持续维护目标、已同意资源和已知缺口。DeepSeek 配置失误就是上下文没有落实为工程事实。
- 当用户批评设计倾向时，先处理该倾向，不能用已修复技术问题的分类解释转移重点。
- 出现同类外部故障时，更早查阅官方机制、平台材料与设备选项。本报告没有新做联网调查；也不把用户后来关闭的设备共享保护写成微信官方普遍限制。
- 让用户复现之前先证明观测有效。没有日志是工具证据不足，不应让用户反复“再试一次”补偿。
- 主动按原需求检查可用性，包括点击目标、保存、重开、取消、错误恢复和数据实际载体。不能等用户发现“只有链接”“没有新增”“结果消失”。
- 报告要短而可操作，细节进文档。过多工程解释和反复许可请求同样消耗协作效率；已授权的安装、构建和安全可逆修复应直接执行。

### 7.3 测试策略应怎样调整

下一次采用五层证据，不相互替代：

1. **规则测试**：时间窗口、去重、任务幂等、输出归一化、过期请求。
2. **真实接口+合成上游**：状态、错误、并发和持久化。
3. **实际宿主 UI**：Service overlay、窗口权限、系统授权、键盘、剪贴板、分享，而非只测 Activity 中组件。
4. **小规模真实链路**：固定设备、账号、客户与必要样本，先核对源数据再调用模型。
5. **业务质量与长期使用**：业务人员依据同一评价表检查画像和建议；另做后台、网络、恢复与不同工作机观测。

数量只在同一层、同一集合内解释。95 项程序回归不是 95 位真实客户；4 项用例在两种配置重跑不是 8 项新业务能力；APK 启动成功不是微信流程通过；用户一次图片发送成功也不能消除其他模拟器失败记录。

## 8. 下次项目的可执行顺序

| 顺序 | 先交付什么 | 进入下一步的判断依据 |
|---|---|---|
| 1. 一页产品约定 | 目标角色、核心任务、排除场景、人工/自动边界、首版范围 | 能写出一条用户完成任务的过程，明确哪些后台配置不应给销售看 |
| 2. 资源与数据小审计 | 设备/系统、平台账号、代表性客户、数据覆盖、现有模型通路 | 明确哪些样本有文本、哪些只具身份资料；既有 key 与生产配置来源已核对 |
| 3. 最短真实纵向链路 | 一个客户从输入、匹配到结果可见，先不铺开全部入口 | 捕获、源数据、生成、返回各有独立证据，不被一个端到端成功掩盖 |
| 4. 业务样本校准 | 真实或脱敏案例评价表，画像/指导/回复/润色各自标准 | 用户认可输出对工作有帮助；信息不足时仍能给合理行动，具体承诺有依据 |
| 5. 状态与异常设计 | 空、加载、成功、旧结果、失败、输入变更、换客户、重启 | 不丢已有工作成果、不串客户，错误告诉用户当前影响与可做什么 |
| 6. 扩展功能与信息结构 | 跟进、素材等完整流程；销售/管理员/诊断分层 | 入口和结果载体真实可用，原需求清单逐项走主路由核对 |
| 7. 发布候选 | 固定签名 APK、对应源提交、服务版本、回滚资料和已知问题 | 验证矩阵有结果；用户接受的缺口被明确记录，不把发布决定等同全验收 |
| 8. 小范围使用复盘 | 真实失败样本、反馈、源数据变化与必要耗时观测 | 再决定优化模型、批量调度、生命周期清理和规模化能力 |

资源条件不齐时，第 3 步可用合成适配器继续，但相应格子保持未验证；不能为了等待理想条件而完全停工，也不能让假数据成功冒充真实链路。

## 9. 本次仍需承接的事项

这些是复盘得到的后续事项，不在本轮写作中自动执行。

**发布记录**：保存 v26 精确源码提交和两仓对应关系；保留当前 APK 校验值；确认对外版本名及 release notes，避免 preview 文件名和产品正式定位产生交付歧义。

**既有验证缺口**：v26 真机键盘、小屏大字体与实际悬浮窗口；已知 OCR 精确误识别；后来图片剪贴板模拟器回读失败；后台提醒与通知实际场景；完整 lintDebug 曾存在错误，缺少最新全量清理结论。不同问题单独登记，不由“正式版”状态自动关闭。

**业务待办**：知识库接入及帮我回质量验收；真实画像与销售指导样本评审；客户生命周期与存储清理；模型选择和夜间批量。平台聊天保存期限、批量历史恢复渠道仍未确认，不能当作现成能力。

**文档一致性**：不少报告保留“尚未部署/未安装”的当时状态，后续对话又有成功回执；两者不是必然矛盾，但应有统一版本账本串联。不能靠修改旧报告抹掉阶段事实，也不能只读旧报告误判当前仍阻塞。

**字段与界面一致性**：本轮只读核对发现 v26 ProfilePresentation 的结构字段标签仍主要列早期字段，而 business-v3 已增加 current_needs、target_clues、current_arrangements 等字段。摘要仍可能承载这些内容，尚未确认造成真实信息遗漏，但值得专门核对“服务端已输出的价值是否在界面显现”，不能把后台字段增加等同前台能力完成。

## 10. 下一步复盘访谈要补什么

初稿已经能形成工程与协作结论，但产品价值部分还缺用户使用证据。后续补充时只需要围绕以下问题，不要求重讲全部历史：

- 哪几个实际场景已经帮助销售，哪些仍让人绕开助手？请给具体操作和结果，不先填满意度分数。
- 哪些输出让你觉得“能用”，哪些虽无明显事实错误却无助于工作？它们用于校准业务评价表。
- 部署、安装、选号、截图、找素材中，哪一步最常需要管理员帮助？
- 首版准备由哪些人员、多少工作机使用？只有落实后才写规模和上线日期。
- 是否有连续工时、费用或使用记录可用于量化？没有就保持定性，不能凭版本数量推算投入。

本稿的核心经验是：**尽早验证产品依赖的真实条件，让技术约束服务业务目标，并把已有结果、原需求和验证边界持续保留下来。**这比单纯追求更多功能或更严密的提示词，更能减少下一个项目的返工。
