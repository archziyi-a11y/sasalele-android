# 首次跟进列表同步失败修复（2026-10-17）

## 已确认现象与原因

在USB连接的 PKW110 / [设备标识已脱敏] 上读取用户当前指定提醒页面，工作号“[工作号已脱敏]”，页面上方实际为“同步未完成，保留上次列表，请稍后重试”，下方为“尚未取得列表”。说明已收到后端同步失败状态，不能当作联系人为空。

针对该工作号作本机只读复现，旧代码首个日期片段返回50条，全部因精确窗口校验被过滤，随后coverage.stop_reason=repeated_page。但并未读取第二页，故“重复页”判断错误。

进一步小页只读检查：请求结束时间为次日00:00:00，方舟返回了结束日期当天更晚的消息；账号、消息ID和联系人ID都存在且属于所请求工作号。接口呈现日粒度包含结束日期行为，上界向上取整到次日午夜会多引入一天。不能把筛选后没有符合条件的数据当作没有翻页进展。

## 修复

sales_activity.py：上界保留当天23:59:59，不滚到次日00:00:00，精确毫秒窗口仍在本地校验；分页进展按返回的有效消息/联系人ID判定，与时间/账号筛选后的条数分离。分页数量上限、重复页保护、双标识范围控制保留。

sales_followups.py：补充固定分类的超时/重复页/扫描上限等诊断，不记录异常原文或正文；首次失败不再假称“保留上次列表”；重试启动清除旧错误，避免正在同步仍显示旧失败；提供仅包含天/页/条数的同步进度元数据。

独立后台方舟读取超时从15秒改30秒，避免在本次真实查询中观察到的偶发超时；不改交互接口的超时，不持续高频重试。

版本 followups-v1.1；保留 sales-business-v3、sales-guidance-v2、work-account-v1。APP v20 无需重装。

## 验证及阶段

同一工作号修复后只读扫描：按本机Python time.time固定滚动15×24小时，Asia/Shanghai显示；59页、2531条命中、121位联系人，本轮接口分页遍历完成，无拒绝行。确切窗口epoch见evidence/scan.json。此结果不是声称方舟同步覆盖全量，也不是生产服务器缓存已生成。

程序回归包含跨日上界、整页时间范围外后仍正确翻到有效消息、首次失败诊断和重试恢复，以及已有业务生成与账号隔离；最终结果见evidence/tests.txt。真实查询未调用模型、不保存聊天正文。生产部署仍需用户通过Workbench执行更新包，随后验收该工作号列表；没有要求用户重复点击刷新或发送消息。
