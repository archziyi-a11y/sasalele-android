# SASALELE 方舟画像、帮我回与润色执行计划

编制日期：2026-10-15，Asia/Shanghai。状态：计划待执行，不代表功能完成或验收通过。

## 1. 本轮目标与边界

打通手机日常闭环：截屏或选图 → OCR名称 → 方舟客户候选 → 人工确认双标识 → 获取该客户对话 → 生成并持久缓存画像 → 根据画像、近期对话及用户输入生成“帮我回”或“润色”草稿。

- 手机是日常操作端，访问现有 HTTPS 服务 https://xiaoshou.yilihuashi.com；沿用工作机授权，不新增销售登录或电脑配对。
- 画像主存储位于现有服务器的持久数据卷，所有已授权工作机按同一双标识复用；手机只保留必要缓存。不同工作号的同名客户不得合并。
- 复用既有画像阶段、标签规则、摘要提示词、方舟客户端和模型配置。模型比较、夜间批量生成、自部署模型、用户分级及生命周期自动清理均不在本轮。
- 飞书不再是主链路必要条件；本轮不写飞书或方舟，不恢复旧批处理，不修改旧探针项目，不自动复制或发送微信消息。
- 本计划明确扩展此前“只读组装、不生成”的范围：允许实现按需画像和真实模型草稿；真实调用前安全核实既有服务端模型配置。当前只写计划，不调用模型、不启动定时任务。

## 2. 现状与关键断点

依据 [源码核查记录](PROFILE-REPLY-REUSE-AUDIT-20261015.md)：

1. `sales_service.recent` 可按双标识读近7天，最多2页、每页50条，返回本次取得范围内最近50条；未证明取得窗口全量或完整历史。
2. `profile_aggregate` 已有画像字段与提示词；`profile_enrich` 整体绑定按日快照和飞书写入，不能直接作为手机接口。
3. 服务端已有 SQLite、确认缓存与 Docker 持久卷；缺生成画像、任务去重、消息覆盖记录和滚动更新。
4. 当前 Android 业务入口仅组装上下文，未调用模型；旧固定示例回复不得作为真实输出。
5. 旧格式化会优先保留较早消息、将未知方向显示成员工；新链路必须修正。
6. 当前全局锁与120秒模型超时不能直接组合使用，否则其他工作机查询可能被阻塞。

## 4. 聊天读取与画像输入

以下是本轮拟采用的初始工程预算，非已验证业务阈值，实施时集中配置并记录实际采用值：

- 首次画像：按需读取目标客户近30天，最多6页×50条；到页数、时间或字符预算即停。明确标为“本次范围画像”，不能称完整历史。无可用文本则返回“聊天不足”，不编造摘要。
- 有画像后的刷新：从上次成功覆盖位置读取，使用重叠窗口与消息ID去重；游标/时间语义先用合成及必要只读响应核验，不假设方舟支持未验证的增量接口。达到上限则标记存在缺口，不把覆盖终点错误推进到当前时间。
- 画像更新使用旧画像与新消息；首次遗漏的早期历史不会因滚动更新自动变完整。主动补充历史作为显式受限刷新，不暗中全量扫描。
- 回复另外读取近期消息，不能把画像覆盖终点当作最新聊天终点；用户补充的最新局面独立标记来源。
- 长度预算优先保留最新消息与关键画像，记录实际纳入消息、截断条数和范围。无法识别的语音、图片等只标记类型，不伪装成已识别正文。
- 时间分别记录服务器抓取时间、方舟消息发生时间、画像生成时间及覆盖终点，统一展示Asia/Shanghai；不将它们相互替代。

## 5. 数据与缓存

采用现有 SQLite，新增表，不破坏现有 `cache` 和设备授权表；不引入新消息中间件或数据库服务。

|数据|键与主要字段|更新规则|
|---|---|---|
|画像版本|account_id＋friend_id＋revision；规则字段、摘要、generated_at、输入/输出指纹、模型与提示词版本、来源、覆盖及截断信息|生成成功且输出验证通过后原子发布；旧任务不得覆盖较新版本|
|生成任务|job_id、双标识、类型、输入指纹、状态、开始/截止时间、尝试次数、安全错误码|同客户相同输入合并；重启将中断任务标为可重试，不无限重放付费请求|
|消息处理检查点|双标识、已处理消息ID/时间、有限重叠去重记录、覆盖缺口|只有成功生成才推进；不建立全量聊天永久归档|
|草稿任务|双标识、画像revision、消息指纹、请求类型、用户输入指纹、状态及有效期|重复点击复用同一次任务；用户主动重新生成可创建新任务；短期结果，不混作永久画像|

身份、消息、画像各自刷新，身份命中不得跳过新消息检查。相同消息且模型/提示词版本未变时不重复生成；策略版本变更可显式重建。

原始聊天只作受限处理输入，默认不长期落盘；画像与草稿本身也是客户数据，不进入Git、APK或普通日志。共享仅限现有授权服务范围，不按名字跨工作号合并。

本轮不设置客户生命周期删除期限；等待用户分级后制定。先记录数据库、画像和日志实际占用，部署前核实磁盘余量，设置运维可见的容量告警。40GB不是画像独占空间。

## 6. 接口与任务约定

拟新增接口，名称在实现时统一，保持已有search/confirm/device授权契约：

- `POST /sales/profile/ensure`：仅接受已人工确认的双标识；返回已有画像与freshness，或任务ID/生成状态。刷新不能绕过确认。
- `GET /sales/jobs/{job_id}`：同一授权范围内读取状态；不凭可猜测任务ID暴露内容；任务与客户双标识一并核验。
- `POST /sales/draft`：双标识、request_type（帮我回／润色）、最新局面、待润色原文及幂等请求ID。润色原文为空明确拒绝；返回任务ID或短期复用结果。
- 现有detail/context改为独立画像优先；飞书历史仅可选来源，飞书不可用不阻断新主流程。来源和时间必须分别展示。

任务状态至少包含queued、running、succeeded、failed、interrupted；前端区分等待、模型未配置、聊天不足、网络失败、模型失败、授权失效和客户失效。

采用持久任务表＋单进程有界worker，初始模型并发1、待处理队列上限20；画像/草稿按同客户串行。超时和上限集中配置。等待或调用模型时不得持有全局业务锁；短数据库事务保护状态提交。客户端退出停止轮询，服务端在界限内收尾，不无限运行。

已有画像但更新失败：保留并标注旧画像；无画像且生成失败：明确失败，不能返回模板假装成功。草稿如使用旧画像或画像缺失，必须显示实际依据；不悄悄换客户或扩大聊天范围。

## 7. 验证清单

1. 已确认客户双标识贯穿消息、画像、任务和草稿；同名跨账号不串数据，未确认目标被拒绝。
2. 首次生成、重复点击、不同工作机并发请求及服务重启后命中持久缓存。
3. 新消息触发更新、无新增不重复生成；失败不推进检查点、不丢旧画像；较旧任务不能覆盖新结果。
4. 分页重复、倒序、同毫秒时间、未知方向、缺字段、超预算及窗口不完整都有正确反馈。
5. 聊天中的指令不改变系统任务；模型输出结构校验、不泄露系统配置；合成事实核对与人工样本核验分别记录。
6. 帮我回与润色均真实调用模型；润色保留原意，缺原文明确提示；不自动复制或发送。
7. 生成期间切客户/新截图/编辑请求，旧响应不覆盖；断网、重试、队列满、授权失效和模型超时有中文反馈。
8. 飞书配置缺失或不可用仍能走新主路径；不触发旧enrich/refetch/upsert和定时任务。
9. 日志、错误响应、提交文件及APK扫描不含凭据和客户正文；已知秘密扫描不是绝对不存在未知秘密的证明。
10. 截图和选图回归：模拟器与真实PKW110 Android15结果分开。真机测试前核实serial和观测就绪；用户手动操作微信，不自动点击、不改变时钟。

真实联调先限定一个已人工确认客户，验证画像来源、聊天方向、覆盖时间和草稿依据，不以单样本通过推断整体准确率。记录从服务收到请求到完成的服务器单调时钟耗时和模型usage；手机端另记录等待，不跨时钟推断网络延迟。

相同原因两次修复仍失败时记录阻碍，不继续无限调参；资源耗尽立即停止。测试失败不得包装为上线通过。
